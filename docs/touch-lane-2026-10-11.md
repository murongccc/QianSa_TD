# 四轨触摸输入交付记录

2026-10-12 更新：触摸区域向上扩展到 Y=352，并增加轨道发光；最新资源与验证结果见 [touch-lane-glow-2026-10-12.md](touch-lane-glow-2026-10-12.md)。下文为首次实现及当时状态的历史记录。

后续 MSlice 处理的当前状态见 [touch-lane-mslice-2026-10-11.md](touch-lane-mslice-2026-10-11.md)。当前绑定层改为 13 拍单比较器处理，工程增加 HFN off；下文保留首次实现的综合记录。最后已验证打包仍超限 22，HFN off 后按用户要求未继续布局，不能视为超限已解决。

2026-10-11，基于 `b96bb93 Optimize FFT interpolation with exact shared arithmetic`。本轮实现手动四轨 Tap/Hold，保留已优化 FFT、SDRAM、触摸解析、十字、双线性缩放、音画、AUTO 和旧签名诊断关闭配置。没有修改判定算法、窗口、厂商 IP、PLL、时钟或管脚。

## 连接与行为

`ch9350_touch_input.update_valid` → `touch_lane_input`（50 MHz）→ `touch_game_event_bridge` → `rhythm_game_engine`（25 MHz video_clk，外部模式 2）。原坐标映射/帧快照/十字仍走自己的显示链；游戏事件不依赖视频帧请求。

绑定层每个接触仅保存编号、live 和四位独热绑定，不保存原始或像素坐标。当前 A/B 按下编号都先查询两个旧身份，再决定是否新接触。区外按下也保存 live 和编号，绑定为零，因此滑入不会产生按下。区内按下后换轨或离开区域仍保持首次绑定，真正松开后才可重新选轨。两个绑定 OR 后产生 `new_down & ~old_down` 与 `old_down & ~new_down`。同轨两指只有最后松开才释放，轨道始终占用时不能交替重复触发 Tap。同报告的所有变化成为一条 12 位事件。

顶层手动模式从 TEST=1 改成外部输入=2；AUTO=0 保持。核心源文件没有改动。

## 操作区参数

默认像素区域 `96 <= x < 544`、`384 <= y < 480`。参数在 `src/touch_lane_input.v`，为等价原始阈值：

| 参数 | 原始阈值 | 对应像素边界 |
|---|---:|---:|
| X0 | 2494 | x >= 96 |
| X1 | 5307 | x >= 208 |
| X2 | 8119 | x >= 320 |
| X3 | 10931 | x >= 432 |
| X4 | 13744 | x >= 544，排除 |
| Y0 | 7584 | y >= 384 |

轨道 0/1/2/3 对应掩码 `1/2/4/8`，区间均左闭右开。Y 没有 raw 上限；沿用映射钳位语义，超过标定最大值仍在屏幕底部。比较器不增加坐标乘除法或 DSP。调整像素区域时应离线重新反推原始阈值；标定变化后必须重新运行阈值验证。

`run_touch_lane_regression.py` 从当前 mapper 读取 X/Y min/max/scale，穷举 65536 个 X 和 65536 个 Y，核对上述区域及每条轨道。当前标定仍为 X=96..16144/2610，Y=128..9440/3371，Q16 加 32768 舍入。

## 跨域、时间、容量与故障

跨域使用四相 req/ack，只有控制位做双触发同步；12 位载荷在 req 发出前写入并保持到 ack 返回。源域有两个 12 位等待寄存器，另有一个传输载荷；目标域有一个待提交载荷。合计最多四条未消费事件，没有大型 FIFO。

第一次完整接收载荷时锁存有符号 33 位 `game_time`，单位为 48 kHz PCM 帧。等待 ready 期间 valid、时间、press、release 和载荷内 down 均保持不变。核心 down 接口保持上一次已提交状态，仅在接受事件的边沿切换为该条事件的 down；源域最新状态不能越过待接收的释放事件。适配层不跨域传输多位游戏时间，不补偿 UART 或触摸设备延迟。

空队列仿真从 source_valid 发出到目标完整接收测得 114/120/150/92 ns（分别为相位/半周期 7/19、0/20、31/23、1/11 ns），包含负数 game_time 的首次锁存断言。板级 20 ns/40 ns 时钟下，空队列从 source_valid 起保守不超过 160 ns，从解析器 update 起另加一拍绑定处理约 20 ns；核心正常接受通常在 1 us 内。它们是 RTL 时序及仿真值，尚未做板上延迟测量。

容量依据：115200 baud、8N1、61 字节触摸帧，校验报告最短间隔约 `610/115200=5.295 ms`。当前 renderer 一次捕获包括首项 COPY 12 拍、后 31 项各 COPY 8 拍，每项两次 SETUP+17 拍 DIVIDE+STORE、进度条最多 448 次相减；捕获约 1927 个 video_clk 周期，保守上限取 4096 拍（163.84 us），加核心有限扫描和握手仍远低于一份报告间隔。正常流量在捕获停止期间不能积累多份报告，因此两项源等待容量有余量；异常长期反压仍可能填满有界队列，不能声称无条件不溢出。保守捕获提交延迟约 0.165 ms，约 8 个 PCM 帧，远小于原最小判定窗 2400 帧（50 ms）。设备自身和串口整帧延迟另计，未校准。

队列满不会覆盖已入队记录。锁存 `overflow`、停止源域游戏输入、同步 `fault` 并接入原会话错误入口，使用原队列故障错误码 10（十六进制 A）。导致溢出的新事件无法保存，当前会话以明确错误结束，必须重开；不能继续声称该会话事件完整。诊断 O 标志不会反压游戏链。

## 会话

桥使能为 `engine_run && !engine_reset && !game_auto`，没有加入 `game_capture`。运行状态为 PREROLL=5、PLAY=6、TAIL=9；PAUSE=7、BUFFER=8、RESULT=10、ERROR=11、退场/清空/停止/装载均停用输入。BUFFER 同样执行清空/重新武装规则。

停用时清除事件有效状态、队列和轨道状态；恢复时桥先等待源域确认停用且旧队列为空，再发出使能。绑定层等待解析器最新有效状态显示 A/B 均松开后才武装。开始、重开、取消、模式切换和暂停恢复时，已按住的手指不会自动生成按下。渲染 capture 仅通过引擎 ready 形成反压，事件保留。单个校验错误及没有新报告都不会自动释放手指。

## 串口

原 T/S 格式及快捷键回显保持。新增同一个 `touch_serial_monitor` TX 仲裁的短行：

```text
L D:3 P:3 R:0 Q:0 O:0
L D:2 P:0 R:1 Q:0 O:0
L D:0 P:0 R:2 Q:0 O:0
```

D/P/R 为四位十六进制掩码。Q 是游戏事件队列曾溢出，O 是四轨串口诊断曾拥塞，两者全局复位后清零；源域 overflow 本身在会话停用时清零。诊断只保存一条 12 位轨道记录（发送期间也占用），不缓存行字符串。没有空位时保留旧记录并锁存 O，游戏继续处理。正常仅轨道变化输出，队列故障首次出现另尝试一条 P/R 为零的故障通知。Q/O 标志即便故障通知遇拥塞也保持可观察，后续 L 行带出。切换会话清空属于管理操作，不伪造一条触摸释放事件。

L 只在手动游戏运行并武装后产生；进入 AUTO、暂停、装载或普通音画模式时仍可观察原 T 行和十字，但没有游戏轨道输入。

## 板上验收顺序与未验证事项

先用既有开关/按键进入手动游戏（模式键 key4，暂停 key3，重开 key2；保持既有会话控制方式），所有手指松开一次，观察十字及 L 行，再验证判定。

1. 区外点击：没有 L 按下；四轨中心依次点击：D/P 分别为 1/2/4/8，松开 R 对应。
2. 区内按住滑到其他轨道或向上移出：十字移动，D 仍绑定原轨。
3. 区外按住滑入：十字移动，没有按下事件；松开重新按才生效。
4. 两指不同轨：组合掩码正确，各自松开互不影响。
5. 两指同轨：第二指不新增 P，松开第一指无 R，最后一指松开才有 R。
6. 按住屏幕重开，或按住暂停/恢复：不会自动触发；全部松开后新的按下恢复。
7. 手动 Tap、双押和 Hold：检查分数、combo、Hold 保持和提前松开失败。
8. 切回 AUTO：原自动演示、十字、串口 T/S、音画继续正常。
9. 检查 Q/O：正常应为零；O 表示诊断文本可能缺行，不能据此判定游戏丢事件；Q 表示游戏输入队列故障，会话应显示错误并重开。

上述新行为尚未在板上验收。UART/屏幕设备延迟未测量、未补偿；上报机制未新增超时释放假设。最终 P&R、bitstream 与下载由用户完成。现有用户未提交的 `current-state.md`、PLL、调试工程、资料/展示目录均未提交或覆盖；主工程工作区中原用户修改经逐字节保留验证，只增添两个源文件条目，提交时只暂存这两个条目。
