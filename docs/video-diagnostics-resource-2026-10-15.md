## 修改

`frame_read_monitor` 的五槽基线原先由五组异步复位的 32 位寄存器和动态读写
多路选择器实现。改成无内容复位、同步读出的两个 BRAM 存储实例；只复位五个有效标志。
使用已有 `EG_LOGIC_BRAM` 原语，按 8×32 声明，槽 0～4 有效，非法槽号仍由
原有判断排除。槽号在整帧期间保持，帧结束前基线已经读出，不增加帧延迟。
TD 将每个 32 位实例映射为两片 BRAM32K，两个实例合计四片，综合总数为 15/16。
中间的自动推断 BRAM 候选映射出八片额外 BRAM9K，使占用达到 67/64，因此已弃用，
没有拿该版本进行布局。分布式 RAM 候选虽保持 BRAM 占用，但实际默认打包仍为
5109 MSlice，未达到容量目标，同样不作为最终交付版本。

这项修改作用于 FIFO 输出监视器 F 和原始 RGB 监视器 D。
保留 B/D/F/C/A 各监视功能、32 位签名算法、五槽独立基线、16 位饱和计数和
现有监视启动条件；没有修改时钟、管脚、厂商 IP 或业务数据链。

顶层的五套计数采样电路改为 `frame_diagnostic_sampler` 共用一套：先按当前数码管页
选择计数，再进行两级同步和连续样本一致检查。页面切换时先清显示，等待页号和数据
流水线排空后更新，约几个 50 MHz 周期，不影响每页两秒的读取。
已启用监视点的事件计数器仍持续独立运行，不会因页面未被显示而漏计。

完整并行模式仍超限，因此增加 `VIDEO_DIAGNOSTIC_POINT`，曾使用 `1` 验证 F 点容量。
用户随后明确要求保留三个监视点同时运行，当前默认恢复为 `0`，保留 RAM 基线和共享采样器优化。
本任务到此暂停；用户先优化其他功能，再继续容量、时序与彩线排查，不再为本次开关恢复运行构建。
未选择的签名监视器不实例化，对应页面跳过，避免显示常量零造成误判。
这是一项诊断方式的取舍：分批构建可保留原签名强度，但不能同时对照三个点。
图片、音频、触摸、游戏及缩放功能不因选择不同诊断点而改变。

| VIDEO_DIAGNOSTIC_POINT | 实例化的签名监视点 | 每两秒轮换的页面 |
| --- | --- | --- |
| 0（当前默认） | D、F、C 全部 | 刷新 → B → D → F → C → A；完整模式容量问题待处理 |
| 1 | F：读 FIFO 输出 | 刷新 → B → F → A |
| 2 | C：SDRAM 返回口 | 刷新 → B → C → A |
| 3 | D：图像处理前原始 RGB | 刷新 → B → D → A |

`VIDEO_SIGNATURE_DIAGNOSTICS=0` 仍会关闭所有签名监视，仅保留刷新、B、A。
修改参数后需要重新综合、布局布线并由用户生成位流。

BRAM32K `15/16`、DSP `19/29`。默认物理流程打包为 `4966/4900` MSlice，
